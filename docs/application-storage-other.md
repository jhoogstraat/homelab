# Application configuration and recovery: infrastructure and home automation

Reviewed against upstream documentation on 2026-10-04. Git owns container images, networking, mounts, proxy routing, hardware access, and initial installation defaults. Application-owned settings belong in writable persistent storage and must survive both container replacement and host image updates. A file-only application can still be configured directly on the device; moving it out of Git does not create a browser editor.

The paths below are **container mount targets**. Use one persistent host storage root with an explicit directory for each application; this deployment uses `/var/lib/homelab/apps/<app>`. Back up the full persistent tree after stopping its writers, including hidden files. Named Podman volumes would still need the same database consistency and recovery procedures and do not provide an independent storage backend.

## Image update policy

Keep Podman's `AutoUpdate=registry` so following a published tag replaces only the relevant containers and does not require a bootc host rebuild or reboot. Existing `stable`, `latest`, and major tags have different upgrade boundaries; document those boundaries rather than claiming they guarantee compatible upgrades. Preserve previous image digests and take a complete state backup before updates: image rollback cannot undo database/schema changes.

Matter.js documents `stable`/`latest`, semver and major tags. HA documents `ghcr.io/home-assistant/home-assistant:stable`. OTBR's maintainer publishes `docker.io/denniswitt/homeassistant-otbr` and `ghcr.io/wittdennis/homeassistant-otbr`, with ARM64 builds; the repository's `ghcr.io/denniswitt/homeassistant-otbr:3` uses the wrong GHCR namespace. Correct to a documented reference while keeping the intended major release unless a separate tested major migration is made. Verify the ARM64 manifest and tag existence during image validation; published docs alone are not evidence that this Pi has successfully pulled or run an image.

## Storage recommendation

Use local POSIX storage for SQLite, application configuration, Home Assistant/Matter/Thread state and credentials. An SSD-backed persistent root plus a uniform directory layout is a sufficient storage boundary on one Pi. Use encrypted deduplicated backups to remote S3; a future Btrfs snapshot design could allow services to resume before uploading; the implemented SD-card baseline stops apps for the entire scan/upload.

Use S3 as a live backend only through an application's native object storage driver. Registry v3 qualifies; it is optional because live S3 introduces an internet dependency for private image pulls. Beszel and HA use S3 for native **backups**, not as interchangeable POSIX data mounts. Do not mount an S3 bucket under these applications with s3fs/rclone/other filesystem adapters: the applications still expect local database locking, directory operations, and failure semantics.
